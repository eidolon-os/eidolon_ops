# 后续需求：用户在 Mobile 自助备份与还原 Host

状态：已记录，按用户 2026-09-11 的决定，留到整体备份还原机制设计时实施；不阻塞本轮 generation/授权简化收尾。

## 已确认的产品需求

- 入口在 Mobile，由用户自己发起备份、选择备份和执行还原，不依赖开发者运行 Ops 命令。
- 体验类似时间机器：完整恢复或换板后仍是原来的逻辑 Host/Owner，恢复原身份、配对关系、配置和用户数据；正常完整恢复不要求原 Mobile 重新配对。
- Owner 与逻辑 Host 一一对应；一个 Mobile 可以管理多个独立 Host，备份与还原必须明确对应哪台 Host。
- 换板恢复与恢复出厂设置分开。后者建立新 Host/Owner 并重新配对，不能冒充迁移。

## 后续统一设计与验收

复用成熟的快照、加密与存储机制。Mobile 提供操作入口和进度，Host 负责一致性备份与恢复执行；先确定整体边界，再选择现成实现，不另造一套底层备份协议。

完整范围包括 Host/Owner 身份及恢复所需的离线签名材料、凭据、全部授权和撤销状态（含 Bootstrap 手机管理授权）、配置与业务数据。现有离线 Owner 私钥主要位于运维工作站，用户自助恢复如何安全获得完整材料是必须解决的架构问题，不能仅给现有局部 CLI 套 Mobile 页面。

统一考虑备份保存位置、加密与恢复凭据、空间不足、失败重试、版本/硬件兼容、恢复中断处理、还原前范围说明和新板恢复的安全入口。存储位置和密钥恢复体验尚未确定，本轮不预设必须用云服务或把全部备份放在手机。

真实验收至少包含：同机恢复、换板恢复、旧板退出使用、原手机自动重连及业务数据可用。旧快照带回已撤销权限、两个副本同时运行的问题必须明确产品规则与技术限制，不能声称 generation 已自动解决。

现有 `backup/restore`、`authority-backup/authority-restore` 继续作为局部运维能力，不能称为整机迁移已完成。
