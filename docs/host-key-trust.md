# 信任按名字记，指纹入库、私钥不入库

两条规则，2026-09-17 各被踩过一次。写下来是因为两次踩法都不像错误：一次什么都没坏，
一次是当场最省事的那条路。

## 一、信任挂在 Host 的名字上，不挂在地址上

传输层用 `StrictHostKeyChecking=yes` 配 `HostKeyAlias={host.hostname}`
（`src/eidolon_ops/transport.py`，三处）。所以 known_hosts 里那一行的键是 Host 的**名字**，
不是这次连上去用的地址。

### 为什么

一台 Host 有好几条链路：USB 网线上的 `169.254/16`、Wi-Fi 上的 DHCP 地址、点对点网线上配置
出来的 `10.42.0.2`。它们上面跑的是同一个 sshd，出示的是同一把 host key。如果按地址记，那么
换一条链路就是一次信任决定——同一块板子，三条链路，三次 TOFU，而其中任何一次都可以被伪造成
"哦这条链路我还没连过"。按名字记之后，**换链路不再是信任决定**，而这正是想要的：链路是可达性，
不是身份。

### 代价，以及为什么它是对的

同一个名字下只能有一把 key。所以两块发布同一个名字的板子不可能同时被信任——换掉
`eidolon-pi5.local` 背后的板子，就是在一个已有 key 的名字下出示另一把，在那之前每个操作都正确地
拒绝。这不是副作用，这是同一条性质的另一面：你没法既让"名字=身份"，又让两个身份共用一个名字。

台架上的 rk3588 把这件事顶到了极限。它的 `hostname` 是 `10.42.0.2`——一个字面地址，理由和退出条件
都写在 `config/eidolon-rk3588.toml` 里（macOS 不在那条 USB 网口上发 mDNS 查询，而
`require_wired_release_upload = true` 需要有线端点）。但那条线是点对点的，一次只接一块板，所以
**每块烧好的板子都是这个地址**。也就是说：这个"名字"是台架上唯一区分两块板子的东西，而每块不同
的板子都会在它底下出示不同的 key。

这块板子今天换过两次。

### 曾经怎么错的

`config/eidolon-rk3588.toml` 的 `known_hosts_file` 一直指着 `~/.ssh/known_hosts`，而且没有
`operator_keys_file`——两半机制都缺。**而什么都没坏**：每个 ops 操作都正常工作了很久。会开口的那一半
只在换板子那天开口，那天它开口的方式是 ssh 大声拒绝，而当时手边最省事的动作是加一个
`-o StrictHostKeyChecking=no` 或者手删一行。

失败方向是诱导性的：删错一行会当场报错，粘一把没核对过的 key 则永远静默。所以这条规则现在由测试
对**每一个** profile 检查（`tests/test_profile_host_trust.py`），而不是对写它时那一个。新板子是写一份
profile，而最容易忘的那一项，恰恰是别的东西都不会报的那一项。

## 二、指纹入库，私钥不入库

`config/<profile>.operators` 是入库的，`config/<profile>.toml` 的 `host.host_fingerprint` 也是。
`host.identity_file` 和 profile 自己的 `known_hosts` 不入库。

### 分界线不是"敏感"，是"公开"

- **指纹**是从公钥算出来的，板子本机 `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` 就会打印给
  任何人看。它没有任何东西可以泄露——它的用途就是被到处传播然后被比对。
- **操作者公钥**同理：公钥是公开的，而"谁可以操作这块板子"是一个应该被评审的决定。
- **板子的私钥**在板子上，哪儿也不去。
- **profile 自己的 known_hosts** 不入库，理由和上面三条都不同：它不是秘密，它是**一台机器的本地
  状态**。

指纹写成 profile 的一个字段而不是一个单独的文件：`.operators` 需要是文件，因为它是一人一行；指纹是
一个标量。为一个标量新建文件，就要配一个解析器、一条"只能有一行"的规则、一个路径字段，以及一个
"它是否被跟踪"的测试——而 profile 本来就是入库的、评审过的，并且已经有 `claim_window` 这种"空字符串
= 没声明"的字段惯例。

### 不入库的那一半，曾经把另一半也带走了

指纹只落在 gitignore 的 `.eidolon-ops/` 里，结果是每台操作机各自 TOFU 一次，第二个操作员手上没有任何
可对照的值——"这是不是那块板子"只能问板子。而 `.operators` 是入库的，注释还专门解释了为什么。这个不
对称看起来是无意的：两个值同样公开，只有一个能跨机器、跨时间传下去。

## 二·五、这个声明买到什么，买不到什么

**这一节是这份文档最要紧的一段。** 这套机制在成形过程中先写成了会撒谎的样子，改掉了，
但那个坑值得留在这儿——它太容易再挖一次。

`trust-host-key --apply` 对照 `host.host_fingerprint`：对得上就写，对不上就并排打出两个值并要求
`--replace`。问题在于**这个声明值是从哪儿来的**。

| | 声明一个值能拦住吗 |
|---|---|
| 此后换板子 | 能 |
| 别的机器上、以后的中间人 | 能 |
| 每台工作站各自 TOFU | 消掉了 |
| **首次扫描那一刻的中间人** | **不能** |

最后一行是关键。如果那个值是把 `trust-host-key` 扫出来的指纹粘进去的，那么对照值来自被对照的那次扫
描——这道闸永远会过，而它声称自己比对过。那是 **pin**，不是 **verification**：

- **pin**：固定住"我们一直在用的这把 key"。此后任何变化都会喊。首次那一刻错了的话，它把错的固定住。
- **verification**：有人从**不是被验证的那条通道**上读到了这个值。串口、接屏幕和键盘、或者 Ops 在起
  机时自己种进去的 key。

最初的写法里，报告会打一句 `Record SHA256:... in <file>`，把循环值直接递到操作员手上，而那个文件自称
"评审过的指纹"。那犯的是和第三节一模一样的毛病：**把最省事的那条路做成了错的那条。** 所以现在报告
不打印扫到的值供粘贴，而是说明非 ssh 的通道有哪些，并说清楚粘贴扫描结果是 pin 而不是确认。这一条有
测试盯着（`tests/test_host_keys.py`：报告里不得出现扫到的指纹）。

台架上的实际状况（2026-09-17 实测）：OPi 只接了一根 USB 网线，没有串口也没有 HDMI；`bring_up.py` 既
不种也不读 host key，板子首次启动自己生成。所以**这台台架今天拿不到任何非 TOFU 来源的指纹**，两个
profile 的 `host_fingerprint` 都是空的。空着是诚实，不是待办——工作站造不出一个没人从板子上读过的值。

### 那能不能让 ops 一步到位

分三件事看，只有第三件是工具做不到的。

**比对**——已经是标准 ops，`trust-host-key` 自己做，不需要任何额外步骤。

**不让声明变陈旧**——也是 ops 的事，而且做法是**删掉一条捷径而不是加东西**。原先
`if replacing or undeclared:` 让一个 `--replace` 同时满足两道闸，于是"profile 声明 X、板子出示 Y"时，
`--replace Y` 把 Y 写进 known_hosts 而 profile 还声明着 X。声明就此变成没人维护的噪音，下一个操作员
遇到的是一个对不上的值，学到的是"加 `--replace` 能过去"。**一个 flag 能推翻的评审值就是装饰。**

现在 `--replace` 只服务本机 known_hosts 那道闸（"这台机器接受一把新 key"，本地决定，命令行说了算）。
声明那道闸只能靠改声明来过——而改完之后就没有冲突需要确认了，`trust-host-key --apply` 直接记录。那次
编辑就是确认本身，并且是下一个人唯一看得见的那个。

**来源**——工具做不到，任何工具都做不到：没有办法验证一个人是从串口读的而不是从 ssh 读的。能做的只有
两件，都已经做了：不把循环值递到手上，以及把"声明"和"本机接受"分成两道各自独立的闸。

真正的出路是物理的：给板子的调试串口接一根 USB-TTL。一次性的，几十块钱，之后每块新板子都能拿到一个
真正确认过的指纹。这比任何代码都管用，也是唯一管用的。

### 一条不该走的路

曾经记在这里的"根除办法"是让 Ops 在 `bring-up` 时生成 host keypair 并随 cloud-init 种进板子，这样指纹
在板子第一次开机之前就是已知量。**这条不该做**，理由写在 `bring_up.py` 的 `BringUp` docstring 里，是这个
模块自己的原则：

> The Host's own Wi-Fi is deliberately absent. ... would make Ops hold a credential for
> something it does not own.

种 host key 正是这件事，而且更重的一层：谁读过那张启动介质，谁就能永久冒充这块板子。它把"板子的身份
属于板子"换成了"板子的身份属于那台工作站"。台架上或许划得来，产品上是取消资格的，而这个仓库的原则
不按台架写。

## 三、顺带：为什么会生成 ssh_config

手动 ssh 一次要三个 `-o` 加一个 `-i`，其中 `HostKeyAlias` 没人会自己想到——命令行上没有任何东西提示
它是承重的。于是正确的路是长的那条，短的那条是 `-o StrictHostKeyChecking=accept-new`，它把一条没人
核过的 key 按地址记进操作者自己的 `~/.ssh/known_hosts`：上面第一条和第二条同时被绕过。

`./eidolon <host> ssh-config --apply` 把 profile 的那套选项渲染成一个 `Host` 块，放在 profile 自己的
目录里，`~/.ssh/config` 顶部 `Include` 一行即可。之后 `ssh eidolon-pi5` 同时是最省事和最正确的路径。
生成而不是手抄，是因为手抄会多出一处 alias 和 known_hosts 路径必须一致的地方，而且是会无声漂移的
那一处：传输层会继续拒绝错的 key，手抄的块却已经悄悄信了。

一条安全机制如果比绕过它更难用，它就只值操作员的自律。
