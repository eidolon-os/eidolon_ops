# 信任按名字记，公钥入库、私钥不入库

两条规则，2026-09-17 各被踩过一次。写下来是因为两次踩法都不像错误：一次什么都没坏，
一次是当场最省事的那条路。第四节记的是同一天试出来又删掉的一个机制。

## 一、信任挂在 Host 的名字上，不挂在地址上

传输层用 `StrictHostKeyChecking=yes` 配 `HostKeyAlias={host.hostname}`
（`src/eidolon_ops/transport.py`，三处）。所以 known_hosts 里那一行的键是 Host 的**名字**，
不是这次连上去用的地址。

### 为什么

一台 Host 有好几条链路：USB 网线上的 `169.254/16`、Wi-Fi 上的 DHCP 地址、点对点网线上配置
出来的 `10.42.0.2`。它们上面跑的是同一个 sshd，出示的是同一把 host key。如果按地址记，那么
换一条链路就是一次信任决定——同一块板子，三条链路，三次 TOFU，而其中任何一次都可以被伪造成
"哦这条链路我还没连过"。按名字记之后，**换链路不再是信任决定**，而这正是想要的：链路是可达性，
不是身份。

### 代价，以及为什么它是对的

同一个名字下只能有一把 key。所以两块发布同一个名字的板子不可能同时被信任——换掉
`eidolon-pi5.local` 背后的板子，就是在一个已有 key 的名字下出示另一把，在那之前每个操作都正确地
拒绝。这不是副作用，这是同一条性质的另一面：你没法既让"名字=身份"，又让两个身份共用一个名字。

台架上的 rk3588 把这件事顶到了极限。它的 `hostname` 是 `10.42.0.2`——一个字面地址，理由和退出条件
都写在 `config/eidolon-rk3588.toml` 里（macOS 不在那条 USB 网口上发 mDNS 查询，而
`require_wired_release_upload = true` 需要有线端点）。但那条线是点对点的，一次只接一块板，所以
**每块烧好的板子都是这个地址**。也就是说：这个"名字"是台架上唯一区分两块板子的东西，而每块不同
的板子都会在它底下出示不同的 key。

这块板子今天换过两次。

### 曾经怎么错的

`config/eidolon-rk3588.toml` 的 `known_hosts_file` 一直指着 `~/.ssh/known_hosts`，而且没有
`operator_keys_file`——两半机制都缺。**而什么都没坏**：每个 ops 操作都正常工作了很久。会开口的那一半
只在换板子那天开口，那天它开口的方式是 ssh 大声拒绝，而当时手边最省事的动作是加一个
`-o StrictHostKeyChecking=no` 或者手删一行。

失败方向是诱导性的：删错一行会当场报错，粘一把没核对过的 key 则永远静默。所以这条规则现在由测试
对**每一个** profile 检查（`tests/test_profile_host_trust.py`），而不是对写它时那一个。新板子是写一份
profile，而最容易忘的那一项，恰恰是别的东西都不会报的那一项。

## 二、公钥入库，私钥不入库

`config/<profile>.operators` 是入库的，`host.identity_file` 和 profile 自己的 `known_hosts` 不入库。
分界线不是"敏感"，是"公开"，而且有两条不同的理由：

- **操作者公钥**是公开的，而"谁可以操作这块板子"是一个应该被评审的决定，不是碰巧躺在某一台笔记本
  `~/.ssh` 里的东西。所以它入库。
- **板子的私钥**在板子上，哪儿也不去。**这台机器连接用的私钥**在操作者自己的 `~/.ssh` 里。
- **profile 自己的 `known_hosts`** 不入库，理由和上面都不同：它不是秘密，它是**一台机器的本地状态**。
  入库它等于把"这台工作站碰巧第一次信了什么"变成所有人的事实。

曾经试过在这儿再加一个入库的指纹文件（"第二个操作员没有可对照的值"）。删掉了，原因记在
[三、什么没做](#三什么没做不是忘了)。

## 三、顺带：为什么会生成 ssh_config

手动 ssh 一次要三个 `-o` 加一个 `-i`，其中 `HostKeyAlias` 没人会自己想到——命令行上没有任何东西提示
它是承重的。于是正确的路是长的那条，短的那条是 `-o StrictHostKeyChecking=accept-new`，它把一条没人
核过的 key 按地址记进操作者自己的 `~/.ssh/known_hosts`：上面第一条和第二条同时被绕过。

`./eidolon <host> ssh-config --apply` 把 profile 的那套选项渲染成一个 `Host` 块，放在 profile 自己的
目录里，`~/.ssh/config` 顶部 `Include` 一行即可。之后 `ssh eidolon-pi5` 同时是最省事和最正确的路径。
生成而不是手抄，是因为手抄会多出一处 alias 和 known_hosts 路径必须一致的地方，而且是会无声漂移的
那一处：传输层会继续拒绝错的 key，手抄的块却已经悄悄信了。

一条安全机制如果比绕过它更难用，它就只值操作员的自律。

## 四、什么没做，不是忘了

**在仓库里存一个 host key 指纹供比对。** 想法是：profile 自己的 `known_hosts` 在 gitignore 里，所以
第二个操作员和新 checkout 各自首次信任，手上没有可对照的值；存一个入库的指纹就有了。

做出来之后删掉了，两个理由：

1. **那个值只能是循环的。** 唯一能读到指纹的通道是 ssh 上去跑
   `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`——而那条连接的信任正是它要确认的东西。工具报告
   里打出扫到的指纹让人粘贴，就是把"自己给自己发绿灯"做成了最省事的那条路。要非循环，得从串口或接
   屏幕键盘读，也就是要为每块板子多一根线。
2. **它补的缺口今天不存在。** `.operators` 里只有一把 key，第二个操作员还没有。而换板子这件事，
   `trust-host-key` 本来就拦得住：已有不同的 key 就要 `--replace`，不需要任何额外的值。

留下的教训比机制值钱：**任何"存一个值用来比对"的机制，先问这个值从哪儿来。如果它和被比对的东西同源，
那这道闸是装饰。** 这条和第三节是同一条原则的两面——一条比绕过它更难用的机制只值自律，一条比它要验证
的东西更容易伪造的机制连自律都不值。

真需要它的那天（有了第二个操作员，或者接了串口），再加不迟，代价也就是一个字段。
